## 先更新：LIAR-RAW 中 `is_evidence` 更准确的含义

严格说，原始 **LIAR** 数据集本身主要是 PolitiFact 上的 12.8K 条短声明，每条声明有人工作出的 truthfulness label，并带有详细分析报告和来源链接；它不是一个原生的句子级 evidence-selection 数据集。([arXiv][1])

你现在用到的句子级 `is_evidence` 字段，更准确地说来自 **LIAR-RAW / CofCED** 这条扩展数据线。CofCED 官方仓库说明 LIAR-RAW 基于 LIAR，gold labels 指向 PolitiFact，并为每条 claim 扩展了额外 raw reports；论文附录也说明 LIAR-RAW 是在 LIAR-PLUS 基础上扩展 raw reports 得到的。([GitHub][2]) ([ACL 论文集][3])

因此，PPT 里建议不要把 `is_evidence=1` 说成“人工标注的 evidence relevance label”。更准确的表述是：

```text
LIAR-RAW 的句子级 is_evidence 更接近：
基于 gold explanation 的文本相似度与语义相似度筛选出的 explanation-oracle / silver evidence label。
```

论文中的定义是：每个句子被标注为 evidence 或 not evidence，是依据它与 gold explanation 的相似度；具体使用 ROUGE 系列分数衡量文本层面的 n-gram overlap，用 cosine similarity 衡量语义层面的相似度，超过阈值的句子被接受为 gold explanation sentences / oracle。([ACL 论文集][3]) ([ACL 论文集][3])

这会影响第 4 页的措辞：核心不是“人工证据标签不可靠”，而是 **explanation-similarity oracle 不等于当前 verifier 的 utility signal**。

# 第 4 页｜第一轮反思：`is_evidence` 不等于 Verifier Utility

### 页面标题

为什么标签句不好用？

### 页面核心句

`is_evidence=1` 表示它像 gold explanation，
但不保证它能让当前 verifier 做出更稳的 label decision。

### 页面正文

在 LIAR-RAW 中，句子级 `is_evidence` 更接近一种 **explanation-oracle label**，在CofCED文章中提到了其标注流程：

```text
candidate sentence
      ↓
与 gold explanation 比较
      ↓
ROUGE / cosine similarity 过阈值
      ↓
is_evidence = 1
```

回答的是：

```text
这句话是否像 gold explanation？
```

但系统真正关心的是：

```text
这句话加入 evidence set 后，
是否能帮助 verifier 判断 claim 的真假？
```

所以使用了原始证据句的负向结果可以解释为：

```text
Explanation similarity ≠ Verifier utility
```

### 页面视觉建议

做成左右对照：

```text
is_evidence label                    verifier utility
──────────────────                  ──────────────────
像 gold explanation                  能改变 / 稳定判断
句子级匹配                           evidence set 级贡献
ROUGE + cosine 相似度                verifier-aware decision gain
可作为弱监督                         不能直接当最终目标
```

右下角放一句醒目结论：

```text
A good explanation-like sentence
is not necessarily a useful evidence set.
```

### 讲稿口播

“这里我想先修正一个容易误解的点。LIAR-RAW 里的 `is_evidence` 不应简单理解成有人逐句判断‘这句话就是事实核查最有效证据’。它更接近一个从 gold explanation 蒸馏出来的 explanation-oracle label：句子和 gold explanation 在 ROUGE 或 cosine similarity 上足够接近，就会被标成 evidence。这个标签当然有价值，但它回答的是‘这句话像不像解释’，不是‘这句话对当前 verifier 有没有判别增益’。所以第 3 页 raw `is_evidence` top5 效果弱，并不等于 dataset 没用，而是说明我们的优化目标需要从 explanation similarity 转向 verifier utility。”

# 第 5 页｜RAG 思想的引入

### 设计思路

1. 从explanation-like sentences 喂给多个 verifier的失败出发，发现瓶颈来源于上游数据，于是聚焦于上游evidence、
2. 依据自身研究方向，引入RAG思想（简要介绍RAG及其作用）
3. 用RAG思想重构该任务

### 页面标题

**RAG 思想的引入**

### 页面核心句

既然单独把这些 explanation-like sentences 喂给 verifier 不够，我们需要重新定义系统结构：先把任务看成一个检索—验证闭环，也就是 RAG。
这里的 RAG 不是“让模型联网查知识”，
而是：**先从 claim 对应的 reports 中选证据，再让 verifier 基于证据判断。**

### 页面正文

在这个项目里：

```text
R = Evidence Retrieval / Selection
G = Verifier 的 label decision
```

输入不是单独的 claim，而是：

```text
claim + raw reports
```

系统先从 report 句子中选出 evidence set：

```text
S_K = Selector(c, C_N(c))
```

再让 verifier 输出 6 类 fact-checking label：

```text
ŷ = Verifier(c, S_K)
```

所以研究对象从：

```text
classifier(claim)
```

变成：

```text
verifier(claim, selected evidence)
```

本项目需要的 RAG 最小定义：先从 report 中取证据，再让 verifier 只基于这些证据判断，不展开完整 IR 背景。

### 页面视觉建议

放一个横向 pipeline：

```text
claim + reports
      ↓
candidate sentences
      ↓
retriever / selector
      ↓
top-k evidence
      ↓
LLM verifier
      ↓
6-class label
```

每个模块只保留一个关键词：

```text
Claim
Reports
Selector
Evidence
Verifier
Verdict
```

### 讲稿口播

“接下来我们把任务重构成 RAG，但这里的 RAG 不是泛泛地让模型去外部网页查知识。我们的外部知识已经限定在每条 claim 对应的 raw reports 里。系统要做的是：先从这些 reports 中选出一组 evidence，再让 verifier 基于 claim 和 selected evidence 输出真假标签。这样一来，研究对象就不再是一个 claim-only classifier，而是一个由 selector 和 verifier 组成的闭环。”

# 第 6 页｜相似度检索与有效证据的错位

### 设计思路

1. RAG相似度检索与fact-checking证据检索的目标错位

### 页面标题

**相似度检索与有效证据的错位**

### 页面核心句

在传统RAG方法中，检索的目标是：“找到和query最相关的句子用于辅助模型生成”，
而事实核查中的RAG不同，需要的是“能证明、反驳或限定 claim 的证据句子”。

### 页面内容

在普通RAG系统中，常使用Embedding（句子内在向量表示）/ BM25（句子外在相似度）等来衡量文本间的相似程度，
因此普通 retrieval 的目标通常是：

```text
evidence 与 claim 越相似越好
```

但 fact-checking 的目标更强：

```text
evidence 是否能帮助判断 claim 的 truthfulness？
```

两者会错位：

```text
高相似度句子可能只是重复 claim
高相似度句子可能来自同一立场
高相似度 top-k 可能高度冗余
高相似度不保证包含决定性事实
```

所以 similarity retrieval 只能作为候选初筛。
后面还需要 selector 继续判断：

```text
这条 evidence 对 verdict 有没有用？
这组 evidence 合在一起是否足够？
```

上传大纲中也把这一页定位为“检索目标错位”：普通 RAG 主要看 evidence 与 claim 的相似度，而 fact-checking 还需要 evidence 是否能提供证明、反驳或限定信息。

### 页面视觉建议

左右两列：

```text
Similarity Retrieval                  Fact-checking Evidence Utility
────────────────────                  ──────────────────────────────
和 claim 语义相近                     能支持 / 反驳 / 限定 claim
单句相关性                            evidence set 的组合贡献
容易重复 claim                         需要新增判别信息
适合作为候选池                         不足以作为最终 selector
```

底部加一句：

```text
Similarity is a filter, not the objective.
```

### 讲稿口播

“RAG 的第一步通常是相似度检索，这在很多问答任务里是合理的。但 fact-checking 的目标不是找一段和 claim 看起来很像的话，而是找能影响 verdict 的证据。比如，一个句子可能高度重复 claim，但它没有提供额外事实；也可能 top-5 全部来自同一篇报道，彼此高度冗余。它们都相关，但对判断真假未必有用。所以相似度在这里更像候选池初筛，而不是最终目标。”

# 第 7 页｜MMR 的引入

### 设计思路

1. 从检索目标错位出发，第一步先打掉纯语义相似，引入MMR
2. MMR简短原理以及作用介绍

### 页面标题

**用MMR平衡相似度与多样性**

### 页面主旨句

依据上面的分析可知，传统RAG的纯相似度目标与当前任务的目标存在错配
那么，有什么方法可以打破只按相似度检索这一目标呢？
有的，那就是MMR（最大边际相关性，Maximal Marginal Relevance）
MMR 做的事情很简单：
**选相关的证据，但尽量不要重复。**

### 页面主要内容

如果直接取 top-k similarity，可能得到：

```text
5 条都很相关
但 5 条都在说同一件事
```

MMR 的选择逻辑是：

```text
下一条 evidence 既要和 claim 相关，
也要和已经选过的 evidence 不太重复。
```

简化公式：

```text
MMR score
= λ × relevance
− (1 − λ) × redundancy
```

其中：

```text
relevance  = candidate 与 claim 的相关性
redundancy = candidate 与已选 evidence 的相似性
λ          = 相关性和多样性的权衡
```
MMR 的直觉不复杂。它不是每次都拿最相似的句子，而是在每一步选择时问两个问题：第一，这条候选证据和 claim 是否相关？第二，它和已经选过的证据是不是太像？如果太像，就要被惩罚。这样做的目的不是直接解决事实核查，而是先避免 evidence set 里出现大量重复信息。

### 页面视觉建议

左侧画 “Top-k failure”：

```text
claim
 ↓
A1  A2  A3  A4  A5
(all similar, all redundant)
```

右侧画 “MMR selection”：

```text
claim
 ↓
A1  B1  C1  D1  E1
(relevant, less redundant)
```

中间放公式：

```text
relevance − redundancy
```

### 讲稿口播

“MMR 的直觉不复杂。它不是每次都拿最相似的句子，而是在每一步选择时问两个问题：第一，这条候选证据和 claim 是否相关？第二，它和已经选过的证据是不是太像？如果太像，就要被惩罚。这样做的目的不是直接解决事实核查，而是先避免 evidence set 里出现大量重复信息。”

# 第 8 页｜lambda 是 MMR 的旋钮

### 设计思路

1. 讲述lambda在MMR中的作用，以及围绕lambda的数值，可以在证据检索中控制evidence selection 的方向

### 页面标题

**可调整的MMR参数lambda**

### 页面主旨

λ 控制 evidence selection 的方向：
**更相关，还是更多样。**

### 页面主要内容

在 MMR 中：

```text
MMR score = λ × relevance − (1 − λ) × redundancy
```

当 λ 较高：

```text
更偏向选择与 claim 最相关的句子
```

当 λ 较低：

```text
更偏向惩罚重复，鼓励多样证据
```

两个极端可以这样理解：

```text
λ = 1：接近 pure top-k relevance
λ = 0：几乎只考虑去冗余 / 多样性
```

本项目中的 fixed-MMR baseline 使用：

```text
λ = 0.7
top_k = 5
```

项目 README 的配置表也显示 retrieval 的默认 `mmr_lambda` 为 0.70，并且 dense / lexical / BM25 的 retrieval 权重分别为 0.70 / 0.20 / 0.10；这说明后续的 MMR 路线不是凭空调参，而是在一个固定检索配置上研究 relevance-diversity trade-off。([GitHub][4])

修复训练-推理不一致后，fixed-MMR 的代表性 λ 点结果如下：

| λ | 描述 | Acc | Macro-F1 |
|---:|---:|---:|---:|
| 0.0 | 最大多样性 | 19.98 | 16.39 |
| 0.3 | 偏多样性 |21.58 | 17.71 |
| 0.7 | 偏相似性 |26.62 | 26.20 |
| 1.0 | 最大相似性 |24.70 | 22.79 |

可以看到，过低的 λ 会过度强调多样性，导致 evidence 与 claim 的相关性不足；λ=1.0 又退回接近 pure relevance，忽略冗余惩罚。当前 fixed-MMR 最强点出现在 λ=0.7，说明这个任务更需要在相关性与证据多样性之间保持折中。

### 页面视觉建议

放一个横向 slider：

```text
λ = 0                                      λ = 1
Diversity / less redundancy      Relevance / similarity
```

在 0.7 处打一个醒目标记：

```text
fixed baseline: λ = 0.7
Acc 26.62 / Macro-F1 26.20
```

下方放四点指标小表，并用一句话总结：

```text
λ is a scalar control,
but evidence utility may not be scalar.
```

### 讲稿口播

“lambda 可以理解成 MMR 的旋钮。lambda 越高，系统越相信相关性分数；lambda 越低，系统越强调不要选重复证据。修复训练和推理不一致后，我们重新看 fixed-MMR 的几个代表点：lambda=0 的 Macro-F1 只有 16.39，lambda=0.3 也只有 17.71；提高到 0.7 后，Acc 到 26.62，Macro-F1 到 26.20；但 lambda=1.0 又下降到 22.79。这说明 fixed-MMR 的最佳点不是纯相关，也不是纯多样，而是一个折中。但它也带来一个问题：事实核查所需要的 evidence utility，可能并不是一个单轴 lambda 能表达的东西。这个问题会自然引出后面的 learned-lambda 和 oracle-lambda 实验。”
