## 1. 现有方法的空缺在哪里

你的观察是成立的，但需要写得更精确。现有 graph-based fact-checking 大致有四类。

第一类是 **graph-as-encoder / graph-as-classifier**。例如 HeterFC 在 FEVEROUS 上构造 word-level heterogeneous evidence graph，然后用 relational graph neural network 做信息传播和预测；它的 graph 节点是词，graph 的主要作用是增强表征，而不是生成人可审计的证据链。这个方向的弱点是解释粒度太底层，最后仍然是 representation learning。([AAAI Publications][1])

第二类是 **KG-as-reasoning scaffold**。KG-CRAFT 从 claim 和 associated reports 构建 knowledge graph，再基于 KG 生成 contrastive questions，之后将 question-answer pairs 汇总成 concise summary，最终把原始 claim 和 summary 交给 LLM 判断 veracity。它的图不是最终可审计的证据链，而是生成 contrastive questions 和 evidence summary 的中间 scaffold；最终 classifier 主要消费的是 summary，而不是原始证据链。([arXiv][2])

第三类是 **subclaim graph + generated explanations**。G-Defense 把 claim 分解成 sub-claims，构造 dependency graph，然后对每个 subclaim 生成 true-oriented 和 false-oriented competing explanations，再把 explanation-enriched graph 编码后做最终预测。它确实比 KG-CRAFT 更接近“解释图”，但核心证据对象已经被 LLM 生成的 explanation 替换，最终仍是把 graph serialization 和 explanations 输入 encoder 分类；其 explanation graph 还在最终预测之后用于总结和展示。([arXiv][3]) ([arXiv][3]) ([arXiv][3])

第四类是 **decomposition/program/question-guided reasoning**。ProgramFC 把复杂 claim 分解成可由函数库执行的 subtasks，并用程序 trace 提供解释；QACheck 通过一系列 question-answer pairs 展示 multi-hop verification 过程；CorXFact 显式识别 claim-evidence correlation 及其支持程度。这些工作都强调可解释 reasoning，但它们没有把“从候选原始证据中选择一条最小 resolving chain”作为核心优化对象。([ACL Anthology][4]) ([ACL Anthology][5]) ([ACL Anthology][6])

因此，你真正应该占据的位置不是“又一个 graph method”，而是：

> **现有 graph 方法大多把 graph 当作隐式表征、question generator、summary scaffold 或 final classifier input；本文把 graph 当作一个可审计的 evidence-chain construction device。**

这句话很关键。它把你的方法从 KG-CRAFT / G-Defense 的竞争语境里抽出来，转向一个更明确的空缺：**graph-to-chain, not graph-to-label**。

## 2. KG-CRAFT 怎么处理，不建议直接说“真实性存疑”

你复现 KG-CRAFT 在 LIAR-RAW 上 F1 只有 26 左右，这个结果可以作为重要信号，但不要在论文或 rebuttal 里说“真实性存疑”。更稳妥的写法是：

> We implemented a KG-CRAFT-style baseline following the public description. Since no identical execution environment, prompts, intermediate KG outputs, and model API states are guaranteed, we report it as KG-CRAFT-style rather than an official reproduction.

KG-CRAFT 公开结果确实有一个非常大的跳跃：其表格中 LIAR-RAW 上 LLM-based contrastive questions 的 F1 是 27.79 / 29.68，而 KG-based contrastive questions 后变成 60.99 / 73.87；full KG-CRAFT 的 LIAR-RAW F1 也报告到 60.99–73.87。这个跳跃和你复现到 26 左右的结果之间确实存在明显 discrepancy，但应将其归因写成“protocol/model/prompt/intermediate artifact mismatch”，而不是质疑真实性。([arXiv][2])

更好的策略是把 KG-CRAFT 放成三类 baseline：

1. **KG-CRAFT-style summary baseline**：按其公开描述实现 KG → contrastive questions → QA → summary → verifier。
2. **KG-CRAFT-style without summary**：把 QA pairs 直接给 verifier，测试 summary 是否造成信息丢失。
3. **KG-CRAFT-style same verifier**：用你的 verifier、同样 token budget、同样 reports、同样 split，保证横向可比。

论文中可以说：

> Our goal is not to dispute reported numbers under different proprietary LLMs and prompts, but to compare whether raw-evidence chains provide a more auditable and token-efficient alternative to KG-guided summarization.

这个表述既避开攻击，又把比较维度转成你的优势：**raw evidence chain、auditability、token efficiency、chain-level diagnostics**。

## 3. 当前方案应该删掉什么

你的新版文件里当前最强线是：

```text
ABC claim-aware evidence units
→ claim/question retrieval union
→ atomic evidence map
→ typed evidence graph
→ budgeted evidence-chain selection
→ QEC prompt
→ label-token verifier
```

这条链很完整，但作为论文方法太像 system pipeline。文件中也已经指出，方法核心不是让 verifier 看到更多 evidence，而是在 verifier budget 下选择 compact、coverage-aware、non-redundant、question-guided 的 evidence chain。

我建议主论文方法压缩成三件事：

```text
candidate evidence units
→ atom-evidence state graph
→ minimal resolving evidence chain
```

其余全部降级为 implementation details 或 ablations。

具体删法如下。

**ABC chunking 不做主贡献。** 你可以保留它作为 evidence unit construction 的一个实现，但主方法不要依赖它。主实验可以用 sentence units / fixed windows / ABC 三个版本说明 robustness。否则审稿人会认为 novelty 同时在 chunking 和 graph selection 上摇摆。

**QD retrieval 不做主贡献。** QD 很容易撞 QACheck、ProgramFC 和各种 question-guided retrieval。建议把 QD 写成 candidate generator 的一种实现，而不是方法核心。你的核心应从“怎么召回候选证据”转到“候选证据已经有了，如何组织成一条 resolving chain”。

**qec_map 不做主贡献，甚至建议从主 prompt 移除 relation 标签。** `relation=support/refute/qualify` 很容易被认为是 pseudo-label shortcut。主 verifier 输入最好只保留：

```text
Step t
Check: <atom/question being checked>
Evidence: <raw evidence text>
```

relation、directness、confidence 可以用于 selector 和 human-facing trace，但不要默认喂给 verifier。你的文件也已经把 qec_min / qec_map 定位为同一证据链的两种 prompt realization，而不是两套算法；这个处理是正确的。

**label-token verifier 不做贡献。** 它只是 downstream judge。你文件中也明确写到 verifier 是 downstream judge，不是最主要创新点；方法贡献应落在 evidence unit construction、atomic evidence map、typed graph selection 和 QEC prompting 这条链上。 我建议进一步收敛：主贡献只落在 **typed graph selection → chain construction**。

**复杂 typed graph edge 不要全都作为 novelty。** 当前有 duplicate、same_source_context、complements、corroborates、tension、bridge_context 等边。建议主方法只保留三类 edge：

```text
addresses / covers: evidence e addresses atom a
stance: evidence e supports / refutes / qualifies atom a
interaction: evidence e duplicates / conflicts / complements another evidence
```

`same_source_context` 和 `bridge_context` 可以合并为 optional context relation；`corroborates` 可以看作 same-stance multi-source complement；不要让边类型显得过多。

## 4. 建议的新核心：Atom-Evidence State Graph

不要再把你的图写成 conventional KG。KG-CRAFT 的粒度是 entity / relation / KG fact；GraphFC 也把 claim 和 evidence 转成 triplet graph，再做 graph-guided planning 和 checking。GraphFC 已经很接近“图式分解 + 逐步检查”，但它的核心是实体关系三元组和 graph matching/completion；你的差异应该是 **claim atom as verifiable state variable + raw evidence as transition trigger**。GraphFC 的公开摘要明确写到它构建 claim graph 和 evidence graph，并通过 graph-guided planning/checking 逐一验证 triples。([arXiv][7])

我建议定义一个 **Atom-Evidence State Graph**：

[
G = (A, E, R)
]

其中：

[
A = {a_1, a_2, \ldots, a_m}
]

是 claim atoms，不是 entities。每个 atom 是 claim 中一个最小可核查语义单元，例如：

```text
who / what / when / where / quantity / comparison / attribution / causal relation
```

[
E = {e_1, e_2, \ldots, e_n}
]

是原始 evidence units，最好是 sentence 或短 chunk。

每条 atom-evidence relation 是：

[
r(e_j, a_i) = (\operatorname{addr}*{ij}, \operatorname{stance}*{ij}, \operatorname{direct}_{ij})
]

其中：

```text
addr: evidence 是否真正检查该 atom
stance: support / refute / qualify / unknown
direct: direct / partial / context
```

但注意：这些字段用于构造和评估 chain，不一定全部暴露给 verifier。

然后定义每个 atom 的状态：

[
s_i^t \in {U, S, R, Q, C}
]

分别表示：

```text
U: unresolved
S: supported
R: refuted
Q: qualified / partially resolved
C: conflicted
```

整条 claim 的状态是：

[
\mathbf{s}^t = (s_1^t, s_2^t, \ldots, s_m^t)
]

一条证据链不是普通 ranked list，而是一串状态转移：

[
z_t = (a_{i_t}, e_{j_t}, o_t, \mathbf{s}^{t-1} \rightarrow \mathbf{s}^{t})
]

其中 (o_t) 是 step operation：

```text
OPEN: 第一次给 unresolved atom 提供直接证据
CORROBORATE: 对已支持/反驳 atom 提供独立印证
CONTRAST: 引入可信冲突证据，使 atom 进入 conflicted/qualified 状态
BRIDGE: 提供必要上下文，使下一步证据可解释
PRUNE-DUP: 识别但不选择重复证据
```

这就是你的核心区别：**graph nodes 很简单，但每一步 evidence 的作用是可解释的状态更新**。它不是 KG-CRAFT 式 entity KG，也不是 G-Defense 式 generated explanation graph，更不是 HeterFC 式 word graph encoder。

## 5. 从“weighted objective”改成“最短 resolving chain”会更像研究问题

你现在的 objective 是：

[
F(S)=
\lambda_{\mathrm{cov}}F_{\mathrm{cov}}
+\lambda_{\mathrm{map}}F_{\mathrm{map}}
+\lambda_{\mathrm{base}}F_{\mathrm{ret}}
+\lambda_{\mathrm{edge}}F_{\mathrm{graph}}
-\lambda_{\mathrm{dup}}F_{\mathrm{dup}}
-\lambda_{\mathrm{bg}}F_{\mathrm{bg}}
-\lambda_{\mathrm{len}}|S|.
]

这个形式比 P1/P2/P3 好，但还是容易被认为是 hand-tuned weighted heuristic。你文件中也建议把 RuleStepSelect 改成 BudgetedMarginalChainSelect，并用 marginal gain 选择 evidence。 但如果要更 novel，我建议再进一步：**不要主打多项加权效用，主打约束式最小链。**

定义：

[
E^*
===

\arg\min_{S \subseteq E}
\operatorname{TokLen}(S)
]

subject to:

[
\operatorname{Resolve}(S, A_{\mathrm{imp}}) \ge \tau_{\mathrm{res}}
]

[
\operatorname{Dup}(S) \le \tau_{\mathrm{dup}}
]

[
\operatorname{Bg}(S) \le \tau_{\mathrm{bg}}
]

[
\operatorname{ConflictUnresolved}(S) \le \tau_{\mathrm{conf}}
]

如果严格约束不可满足，再改成 soft constrained objective：

[
E^*
===

\arg\min_{S \subseteq E}
\operatorname{TokLen}(S)
+
\lambda_u \cdot \operatorname{UnresolvedAtoms}(S)
+
\lambda_c \cdot \operatorname{UnresolvedConflicts}(S)
+
\lambda_d \cdot \operatorname{DuplicateEvidence}(S)
+
\lambda_b \cdot \operatorname{BackgroundDrift}(S).
]

这个版本比大杂烩式加权 reward 更清楚，因为研究问题变成：

> 在尽量少的 evidence tokens 下，使重要 atoms 达到可判定状态，并避免重复、背景漂移和未解析冲突。

这就是 “Minimal Resolving Evidence Chain”。

算法上可以用 greedy，但论文表达应是：

```text
We solve a minimum resolving chain problem with a greedy transition search.
```

而不是：

```text
We use a graph-aware weighted selector.
```

前者是问题定义，后者是工程策略。

## 6. Chain 的关键：必须有“状态更新”，否则还是 ranked list

要摆脱“只是 evidence list”的质疑，必须让每一步有明确的 before/after state。

主 prompt 可以这样渲染：

```text
Claim:
<claim>

Evidence Chain:
[1] Check atom A2: <atom text>
Evidence: <raw evidence sentence>

[2] Check atom A4: <atom text>
Evidence: <raw evidence sentence>

[3] Check atom A2 again for possible conflict:
Evidence: <raw evidence sentence>
```

human-facing trace 可以这样展示，但不要全部喂给 verifier：

```text
Step 1
Target atom: A2
Before: unresolved
Operation: OPEN
Evidence: ...
After: supported

Step 2
Target atom: A4
Before: unresolved
Operation: OPEN
Evidence: ...
After: refuted

Step 3
Target atom: A2
Before: supported
Operation: CONTRAST
Evidence: ...
After: qualified / conflicted
```

这里的 novelty 是：

> evidence chain is a sequence of atom-state transitions.

不是：

> evidence chain is a sorted subset of graph nodes.

如果你能把每个 case 的 chain 画成：

```text
A1: U → S
A2: U → R
A3: U → Q because evidence e5 conflicts with e2
```

这会比 KG 图或 subclaim graph 更直观。

## 7. 和 KG-CRAFT / G-Defense 的差异应该这样写

建议相关工作中放一个非常清晰的对照表。

| 方法类型                       | 代表方法                | Graph 的作用                                | 最终 verifier 看什么                              | 你的差异                                                        |
| -------------------------- | ------------------- | ---------------------------------------- | -------------------------------------------- | ----------------------------------------------------------- |
| Graph encoder              | HeterFC / GNN-style | 学习 evidence representation               | graph embedding / encoded context            | 你的 graph 不用于黑箱编码，而用于产生可审计 chain                             |
| KG scaffold                | KG-CRAFT            | 生成 contrastive questions 和 summary       | evidence-based summary                       | 你的方法不生成 summary，保留 raw evidence chain                       |
| Subclaim defense graph     | G-Defense           | 组织 subclaims 和 competing explanations    | graph serialization + generated explanations | 你的节点是 claim atoms 和 raw evidence，不依赖生成解释作为证据                |
| Triplet graph checking     | GraphFC             | claim/evidence triplet planning/checking | triple-level checking result                 | 你的 atom 不限于 entity triples，重点是 raw evidence chain selection |
| Program/question reasoning | ProgramFC / QACheck | 程序或 QA trace                             | subtask results / QA pairs                   | 你的 trace 是 evidence-grounded transition chain               |

这张表可以直接成为 related work 里的定位段落。

核心差异句可以写成：

> Unlike KG-based methods that decompose reports into entity-level knowledge graphs or summarize graph-derived QA pairs, we use claim atoms as state variables and raw evidence units as transition operators. The graph is not consumed as a whole by a classifier; it is compiled into a compact evidence chain whose steps explicitly resolve, corroborate, or qualify atomic claim components.

这比“我们的图更简单”更有力。不是简单为简单，而是 **node abstraction matches the unit of verification**。

## 8. 建议主方法改成三模块

最终论文方法可以只保留三个模块。

### 8.1 Atomization

输入 claim (c)，输出 claim atoms：

[
A = {a_1,\ldots,a_m}.
]

每个 atom 有两个属性即可：

```text
text
importance: core / auxiliary
```

不要再放太多 type。type 可以用于分析，但不是主算法必须条件。

### 8.2 Atom-Evidence State Graph Construction

输入候选 evidence (E)，构建：

```text
atom-evidence edges:
    e addresses a
    e supports/refutes/qualifies a
    e is direct/partial/context for a

evidence-evidence edges:
    duplicate
    complement
    conflict
```

这里的 evidence map 就变成 graph edge induction，不再是一个单独模块。你当前文件中 evidence map 包含 covered_atom_ids、relation、directness、role、key_spans、duplicate_group、confidence 等字段，这些字段应该被重新表述为 Atom-Evidence State Graph 的 edge labels，而不是 pipeline 里的一个 preprocessing artifact。

### 8.3 Minimal Resolving Chain Search

选择证据链：

[
Z^* = (z_1,\ldots,z_T)
]

每个 step：

[
z_t = (a_{i_t}, e_{j_t}, o_t).
]

目标是最小化 token，同时最大化 resolved important atoms：

[
\min_Z
\operatorname{TokLen}(Z)
+
\lambda_u \operatorname{Unresolved}(Z)
+
\lambda_c \operatorname{UnresolvedConflict}(Z)
+
\lambda_d \operatorname{Duplicate}(Z).
]

贪心版本：

```text
Initialize all atoms as U.
At each step, choose the evidence that gives the largest valid state transition:
    1. resolves an unresolved core atom;
    2. resolves a conflict or qualifies an over-strong atom;
    3. adds independent corroboration for a core atom;
    4. otherwise stop.
Reject evidence if it is duplicate, background-only, or does not change atom state.
Return the shortest chain that satisfies the resolution threshold.
```

注意这里的 stopping criterion 不再是 “min=5 max=10”，而是：

```text
stop when no candidate evidence changes the atom-state vector enough.
```

这会更像 reasoning，而不是 top-k engineering。

## 9. 不建议继续强化的方向

有几个方向短期内不要做成主贡献。

**不要主打 conflict-aware unless 你真的能区分冲突类型。** 当前 tension edge 如果只是“有冲突就加分”，会被质疑。你文件中也指出 tension 应细分为 credible_tension、temporal_tension、definition_tension、scope_tension、measurement_tension 等，并区分高质量冲突和低质量噪声。 如果时间有限，主文先写成 “conflict exposure / conflict resolution diagnostics”，不要写成 full credibility-aware conflict reasoning。

**不要主打 ordinal verifier。** 这会把论文焦点带偏。ordinal loss 是合理增强，但它属于 verifier 改良，不是 evidence-chain novelty。保留为 appendix 或 future work。

**不要主打 QEC prompt。** QEC 是 rendering，不是核心。你可以说 selected chain is rendered as question-guided evidence steps，但不要把 qec_min / qec_map 作为两个方法。当前文件也建议把两者写成 prompt sensitivity。

**不要主打 dataset-specific policy。** RAWFC tight / LIAR-RAW normal 容易显得针对数据集调参。主方法尽量统一，tight policy 放附录。

## 10. 实验应该围绕“图到链”的 novelty 设计

你不需要做很多泛泛的消融。应该集中验证四个问题。

### 10.1 Graph-to-chain 是否优于 graph-to-classifier？

这是最关键实验。

比较：

```text
Top-k evidence list
Full graph serialization → verifier
KG-CRAFT-style summary → verifier
G-Defense-style subclaim explanations → verifier
Your minimal resolving chain → verifier
```

如果你的 chain 在更少 token 下优于 full graph serialization 和 summary baseline，就能证明：

> graph should be compiled into evidence chains rather than directly consumed by the classifier.

这正好打中你想表达的主创新。

### 10.2 状态转移是否真实有效？

做人工标注或 LLM-as-judge 评估每个 chain step：

```text
Does evidence e address atom a?
Does e change the atom state?
Is the operation OPEN / CORROBORATE / CONTRAST / BRIDGE valid?
Is this step necessary?
```

报告：

```text
Atom addressing accuracy
Transition validity
State update accuracy
Necessary step ratio
Invalid bridge ratio
Duplicate step ratio
```

这比普通 evidence F1 更贴合你的方法。

### 10.3 chain order 是否有意义？

做 order ablation：

```text
ordered resolving chain
randomly shuffled selected evidence
reverse order
grouped-by-retrieval-score order
grouped-by-atom order
```

如果你的 method 号称是 chain，那么 ordered chain 应该至少在解释指标上明显优于 random order；如果最终 F1 不敏感，也可以说 prediction is order-robust but explanation validity depends on transition order。不要强行说 order 一定提升 F1。

### 10.4 最小性是否成立？

做 deletion test：

```text
remove highest-gain step
remove first OPEN step
remove conflict step
remove corroboration step
remove random step
```

报告：

```text
prediction drop
gold-label probability drop
unresolved atom increase
transition invalidation rate
```

你文件中也已经建议 evidence sufficiency / necessity / robustness / cross-verifier transfer，因为只报告 Macro-F1 不足以证明 selected evidence chain 的价值。

## 11. 对 KG-CRAFT 的复现实验应该怎么写

你可以把 KG-CRAFT 作为 **不可忽视但不正面攻击** 的对照。

建议实验表中写：

```text
KG-CRAFT-style reimplementation
KG-CRAFT-style w/o generated summary
KG-CRAFT-style QA-pairs only
KG-CRAFT-style same verifier
MREC raw-chain same verifier
```

报告时分开：

```text
Published KG-CRAFT numbers
Our KG-CRAFT-style reproduction
```

并加脚注：

> Published KG-CRAFT results rely on specific LLMs, prompts, KG construction, and generated intermediate artifacts. Since exact intermediate outputs are not available in our setting, we report our implementation as a style baseline rather than an official reproduction.

这能保护你。你不需要证明 KG-CRAFT 是错的，只需要证明：

```text
在同一 verifier、同一 reports、同一 token budget 下，raw resolving chain 比 KG-guided summary 更可控、更可审计。
```

KG-CRAFT 的一个天然弱点是最终把 QA pairs 汇总为 summary，并以 summary 作为主要 evidence source；你的方法可以强调不做 evidence distillation，不用生成式 summary 替代原文。KG-CRAFT 公开描述中明确写到 QA pairs 会被 summarised into a concise paragraph，claim veracity assessment 只使用 original claim 和 produced summary。([arXiv][2])

## 12. 论文贡献建议改写

不要写：

```text
We propose an Atom-Fact Anchored QEC framework with ABC chunking, QD retrieval, evidence map, typed graph, budgeted selection, and QEC prompt.
```

建议写成：

```text
We formulate fine-grained fact verification as a Minimal Resolving Evidence Chain problem, where a claim is represented as a set of atomic verifiable states and evidence units act as transitions that resolve, corroborate, or qualify these states.

We introduce an Atom-Evidence State Graph, a lightweight graph representation whose nodes are claim atoms and raw evidence units rather than entity-level KG triples. Unlike graph-to-classifier methods, our graph is compiled into an auditable evidence chain.

We propose a greedy transition search algorithm that selects the shortest verifier-budgeted chain maximizing important atom resolution while avoiding duplicate evidence, background drift, and unresolved conflicts.

We evaluate not only veracity prediction, but also chain validity, atom-state resolution, minimality, deletion-based necessity, and graph-to-chain interpretability.
```

中文可以写成：

```text
本文将细粒度事实核查重新形式化为 Minimal Resolving Evidence Chain 问题：claim 被表示为一组待解析的原子状态，原始证据单元作为状态转移操作，逐步将 claim atoms 从 unresolved 推进到 supported、refuted、qualified 或 conflicted。

本文提出 Atom-Evidence State Graph。不同于实体级 KG 或将整图输入分类器的方法，该图只包含 claim atoms 与 raw evidence units，并被编译为一条可审计证据链。

本文提出基于状态转移的 greedy chain search，在 verifier token budget 下选择最短证据链，同时最大化重要 atom 的解析率并抑制重复证据、背景漂移和未解析冲突。

实验不仅评估最终 veracity prediction，还评估 chain transition validity、atom resolution、minimality、necessity 和 graph-to-chain interpretability。
```

## 13. 方法图建议

论文图不要画成 pipeline：

```text
ABC → retrieval → QD → map → graph → selector → QEC → verifier
```

这会显得工程化。

建议画成：

```text
Claim
  ↓ atomization
A1  A2  A3  A4          Raw evidence candidates
 │   │   │   │             e1 e2 e3 e4 e5 ...
 └── Atom-Evidence State Graph ──┐
                                 ↓
                    Minimal Resolving Chain
                    Step 1: A2 U→R via e3
                    Step 2: A1 U→S via e1
                    Step 3: A3 U→Q via e5/e7 conflict
                                 ↓
                          Verifier
```

视觉上要传达：

```text
graph is not the output;
chain is the output.
```

这就是和 G-Defense / KG-CRAFT 最大的叙事差异。

## 14. 最小可投稿版本

如果要最快把方案变得干净，我建议主系统如下：

```text
Input:
    claim c, associated reports R

Step 1:
    Split reports into sentence-level or short evidence units.
    Use any retriever to get top-N candidates.
    Retrieval is not the contribution.

Step 2:
    Decompose claim into atoms A.

Step 3:
    Induce Atom-Evidence State Graph:
        evidence-addresses-atom
        evidence stance toward atom
        evidence duplicate/conflict/complement relation

Step 4:
    Run Minimal Resolving Chain Search:
        choose evidence steps that change atom states
        minimize tokens
        avoid duplicates/background
        expose unresolved/conflicted atoms

Step 5:
    Render chain to verifier:
        Check: atom text
        Evidence: raw evidence text
    Do not expose relation labels in main prompt.

Output:
    veracity label + optional auditable chain.
```

这个版本的主方法只有一个创新核心：**从 atom-evidence graph 到 minimal resolving chain**。

## 15. 最关键的改进点

我会优先做这五个改动。

第一，**把 evidence map 改名为 atom-evidence state graph induction**。这不是换名字，而是改变论文读法：map 不再是 preprocessing，而是你的中间表示。

第二，**把 selector 改成 shortest resolving chain search**。少用 (F(S)) 的多项加权，多用“状态转移 + 最小链 + 约束满足”。

第三，**主 prompt 用 qec_min，不用 qec_map**。relation/directness 可以用于解释和消融，但主结果不要让 verifier 直接看到 support/refute/qualify 标签。

第四，**加入 full graph serialization baseline**。这比普通 top-k baseline 更重要。如果 full graph 输入 verifier 不如你的 chain，就能直接证明“不是图越多越好，而是图要被编译成链”。

第五，**加入 chain validity / minimality diagnostics**。这是你区别于 KG-CRAFT、G-Defense 的核心证据。KG-CRAFT 强在 reported F1，G-Defense 强在 generated explanations；你的强点应该是 step-level auditability。

---

## 16. 最终定位

你现在不应该把论文定位成：

> A graph-based fact-checking framework.

这太宽，也容易撞 KG-CRAFT、G-Defense、GraphFC、HeterFC。

应该定位成：

> A graph-to-chain method for atom-level evidence organization in fine-grained fact verification.

更完整一点：

> We do not use graphs as opaque encoders, KG scaffolds, or summary generators. We use a lightweight atom-evidence graph to compile raw reports into minimal resolving evidence chains, where each step explicitly updates the verification state of a claim atom.

这就是你最有辨识度的 novelty。
