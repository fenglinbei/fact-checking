## 结论

你的怀疑基本成立，但当前实现中存在两个不同含义的 `select score`：

1. **checkpoint selection score**：训练过程中决定哪个 checkpoint 被保存为 `best`；
2. **evidence-chain selection score**：graph selector 决定选择哪些 evidence。

从代码和现有日志数值看，**最可能直接造成 val/test gap 的是第一个，而不是第二个**。当前 checkpoint 并非默认按 Macro-F1 选择，而是：

[
S_{\mathrm{ckpt}}
=================

\mathrm{MacroF1}
+
0.5\times
\frac{F1_{\mathrm{mostly\text{-}true}}+F1_{\mathrm{true}}}{2}.
]

v0.7 配置继承了基础配置，但没有覆盖该 metric，因此会落入 trainer 的默认 `macro_f1_plus_true_side`；推理阶段又默认加载 `best` checkpoint。([GitHub][1])

因此，我建议先修 checkpoint selection，再改 evidence selector。否则两者同时修改后，很难确定 gap 到底来自哪里。

# 1. 当前 checkpoint selection score 存在明显目标错位

设六个类别的 F1 分别是 (f_1,\ldots,f_6)，其中后两个为 `mostly-true` 和 `true`。当前 score 等价于：

[
S_{\mathrm{ckpt}}
=================

\frac{1}{6}\sum_{i=1}^{6}f_i
+
\frac{1}{4}(f_5+f_6).
]

这意味着：

* 其他四个类别的单类权重是 (1/6\approx0.1667)；
* `mostly-true` 和 `true` 的单类权重是：
  [
  \frac16+\frac14=\frac5{12}\approx0.4167;
  ]
* 后两个类别分别获得其他类别 **2.5 倍**的 checkpoint-selection 权重；
* 归一化后，两个 true-side 类占整个选择目标约 **55.6%**，尽管它们只占六个类别中的两个。

这不是一个轻微偏好，而是明显改变了模型选择目标。

它容易产生如下情况：

```text
checkpoint A:
    validation Macro-F1 一般
    mostly-true / true 很好
    selection score 很高
    被保存为 best

checkpoint B:
    validation Macro-F1 更均衡
    false-side 类别更好
    selection score略低
    被丢弃
```

一旦 val/test 在类别比例、类别难度或 true-side evidence 表达上存在差异，checkpoint A 的测试 Macro-F1 就可能显著下降。

## 2. 现有日志几乎可以反推出这个问题

你当前方法记录中有：

* `qec_map`：test Macro-F1 = 0.3587，selection = 0.7686；
* `qec_min`：test Macro-F1 = 0.3578，selection = 0.7765。

按照当前公式反推 true-side Macro-F1：

[
2(0.7686-0.3587)=0.8198,
]

[
2(0.7765-0.3578)=0.8374.
]

也就是说，日志中的 `selection` 数值与：

```text
Macro-F1 + 0.5 × true-side Macro-F1
```

高度一致。

这说明目前所谓的 “best checkpoint” 很可能主要是在挑选 `mostly-true` 和 `true` 表现最好的模型，而不是六分类整体最均衡的模型。旧版方法说明中也把 selector score 和最终 verifier evaluation 混合在一条工程链中，容易造成术语混淆。

建议立即把日志字段重命名：

```text
selection_score
    ↓
checkpoint_selection_score
```

而 graph selector 的分数改名：

```text
chain_objective_score
```

# 3. 第一优先级修复：改为 full-val Macro-F1 选择 checkpoint

在当前 v0.7 experiment 配置中显式覆盖：

```yaml

  mini_val_size: 0

  label_token_ce:
    early_stopping_metric: macro_f1
    true_side_metric_weight: 0.0

  logit_adjust:

```

其中最关键的是：

```yaml

```

同时建议修改 trainer 默认值，防止其他实验忘记覆盖。

```diff
def _selection_score(metrics, label_cfg):
    metric = str(
        label_cfg.get(
            "early_stopping_metric",
-           "macro_f1_plus_true_side",
+           "macro_f1",

    ).strip().lower()
```

保存 metadata 的默认值也应同步修改：

```diff

    "early_stopping_metric",
-   "macro_f1_plus_true_side",
+   "macro_f1",
```

```yaml

```

但不应继续作为默认主实验协议。

## 4. 不必先重训：直接重评所有现有 checkpoints

最有效率的诊断方式不是立即重新训练，而是：

1. 找出一个 run 下所有 checkpoint；
2. 在**完整 validation set**上重新推理；
3. 保存每个 checkpoint 的：

   * Macro-F1；
   * 六个 per-class F1；
   * accuracy；
   * confusion matrix；
   * prediction class distribution；
   * ordinal MAE；
   * eval loss；
4. 重新选择 validation Macro-F1 最大的 checkpoint；
5. 冻结 checkpoint 后，再执行一次 test。

建议输出：

```text
step,macro_f1,true_side_f1,current_selection_score,
f1_pants_fire,f1_false,f1_barely_true,
f1_half_true,f1_mostly_true,f1_true,
ordinal_mae,eval_loss
```

然后比较：

```text
current best alias
vs.
best_macro_f1 checkpoint
```

这一实验可以直接回答：

> val/test gap 是 checkpoint selection metric 导致的，还是 evidence selector 导致的？

若 `best_macro_f1` 的 test Macro-F1 明显提高，那么主要问题已经定位，不需要立即大改 graph selector。

# 5. 更稳健的 checkpoint 选择：one-standard-error rule

单纯取 validation Macro-F1 最高点，仍然可能在大量 checkpoints 中对 validation noise 过拟合。建议使用如下规则：

1. 找出最高 validation Macro-F1：
   [
   F_{\max};
   ]
2. 用 bootstrap 估计其标准误：
   [
   \mathrm{SE}_{\max};
   ]
3. 从满足
   [
   F_{\mathrm{ckpt}}\ge F_{\max}-\mathrm{SE}_{\max}
   ]
   的 checkpoints 中，选择**最早的 checkpoint**。

这相当于选择性能与最优点统计上接近、但训练程度更低的 checkpoint，通常比直接选择单个尖峰稳健。

简化实现可以不用 bootstrap，采用固定容差：

```python
MACRO_F1_TOLERANCE = 0.002

if macro_f1 > best_macro_f1 + MACRO_F1_TOLERANCE:
    update_best()
elif abs(macro_f1 - best_macro_f1) <= MACRO_F1_TOLERANCE:
    # Prefer the earlier checkpoint or lower ordinal MAE.
    tie_break_by_ordinal_mae_then_step()
```

推荐选择逻辑为：

```text
primary: validation Macro-F1
tie-break 1: lower ordinal MAE
tie-break 2: earlier checkpoint
```

不要再把多个评价指标线性相加。线性相加会把 checkpoint selection 变成另一套隐式任务定义。

---

# 6. 第二个放大因素：logit adjustment 默认 `tau=1.0`

基础配置启用了 logit adjustment，代码根据训练类别先验执行类似：

[
z'*y=z_y-\tau\log p*{\mathrm{train}}(y),
]

当前 (\tau=1.0)。([GitHub][2])

这本身不是错误，但会带来两个问题：

1. (\tau=1) 是很强的先验修正；
2. 如果 validation 和 test 的类别比例或类条件 logit 分布不同，validation 上最优的 calibration 可能在 test 上失效。

建议先执行一个干净对照：

```yaml
sft_train:
  logit_adjust:
    enabled: false
```

之后只在 validation 上搜索：

[
\tau\in{0,;0.25,;0.5,;0.75,;1.0}.
]

选择标准仍然是完整 validation Macro-F1，选定后冻结。不要默认认为 (\tau=1) 最合适。

特别要确保：

```text
训练时 validation metric 的 logits 处理
=
最终 test inference 的 logits 处理
```

若一个阶段应用 logit adjustment、另一个阶段没有应用，也会产生明显 gap。

---

# 7. 第三个放大因素：mini-val 若启用，目前不是分层抽样

当前 mini-validation sampling 是普通随机选择，并未按六个类别分层。小 validation 子集上的 per-class F1 本身就很不稳定；再叠加 true-side 加权后，checkpoint selection variance 会进一步放大。([GitHub][3])

仓库默认配置未必启用了 mini-val，但需要检查你之前实际运行的 resolved config 和命令行参数。

正式实验建议：

```yaml
mini_val_size: 0
```

即使用完整 validation set 选择 checkpoint。

算力确实不足时，mini-val 只能用于训练过程监控，不能用于生成最终 `best` alias。最终 checkpoint 必须在完整 validation set 上重评。

若必须构造 mini-val，应至少按以下字段分层：

```text
gold label
report-length quartile
claim atom-count bucket
```

其中 label stratification 是最低要求。

# 8. evidence selector 的 score 也确实存在泛化风险

修复 checkpoint selection 后，第二阶段再处理 graph selector。

当前 marginal objective 中的大致权重为：

```text
coverage             1.00
map_quality          0.06
base_score           0.03
key_span             0.02
complements          0.18
corroborates         0.14
conditional_tension  0.14
bridge               0.07
duplicate penalty    0.30
background penalty   0.16
same-source penalty  0.10
length penalty       0.06
```

并采用固定的：

```text
target_coverage = 0.80
stop_gain = 0.10
insufficient_gain = 0.05
```

这些是跨样本、跨 split 共用的绝对尺度。([GitHub][4])

主要有四个问题。

### 8.1 特征被部分重复计算

`evidence_map_quality_score` 本身已经组合了：

```text
atom coverage
directness
polar relation
confidence
key span
background penalty
```

外层 objective 又单独加入：

```text
coverage
key_span
background penalty
```

因此 atom coverage、key span 和 background 实际被重复计权。([GitHub][5])

这会使 selector score 对 evidence-map calibration 非常敏感。若 validation 与 test 的 atom 数量、map confidence 或 directness 分布不同，score 的相对尺度也会改变。

### 8.2 绝对停止阈值没有样本内归一化

固定：

[
\Delta F<0.10
]

并不代表不同 claim 上相同程度的“新增价值”。

在一个 candidate score 普遍较高的样本中，0.10 很低；在另一个 score 普遍较低的样本中，0.10 又可能过高。最终造成：

* val 上平均选择 6–7 条；
* test 上可能只选择 3 条或强制补足；
* 或者 test 上图边更密，持续选到上限。

### 8.3 pairwise graph utility 随图密度增长

`complements/corroborates/tension/bridge` 作为 pairwise utility 累加时，候选图越密、已选 evidence 越多，新增节点就越容易获得更多边奖励。

因此 objective 不只取决于 evidence 质量，还取决于：

```text
candidate pool density
atom count
report count
source duplication
map relation frequency
```

若这些统计量在 val/test 间不同，score 会出现结构性偏移。

### 8.4 context evidence 同时受奖励和惩罚

当前节点构造中，`directness=context/none` 可以被视为 background；但相同 evidence 又可能通过 `bridge_context` 获得正向奖励。([GitHub][4])

这使 selector 的最终决策依赖多个手工项之间的相消，解释性和稳定性都较差。

# 9. 推荐替换为 Calibrated Atom-Resolution Selector

建议不要继续微调现有十几个权重，而是把 score 简化为：

> 主要优化 atom resolution；图关系只作为受限的 secondary gain；重复、背景和长度改成硬约束。

## 9.1 Soft atom resolution

对 atom (a) 和 evidence (e)，定义：

[
q(e,a)
======

\mathbf 1[e\text{ covers }a]\cdot d(e,a)\cdot c(e,a),
]

其中可以先使用：

[
d(e,a)=
\begin{cases}
1.0,&\text{direct}\
0.65,&\text{partial}\
0.20,&\text{context}\
0,&\text{none}.
\end{cases}
]

atom 在集合 (S) 下的解析程度定义为：

[
R_a(S)=1-\prod_{e\in S}(1-q(e,a)).
]

这样，多条证据可以逐渐提高 atom resolution，但收益递减，不会因为相同 atom 有很多证据而无限累加。

整体覆盖：

[
\operatorname{Resolve}(S)
=========================

\frac{\sum_a w_aR_a(S)}
{\sum_aw_a}.
]

---

## 9.2 简化目标函数

建议使用：

[
F(S)
====

\operatorname{Resolve}(S)
+
0.10,\operatorname{RankUtility}(S)
+
0.08,\operatorname{IndependentCorroboration}(S)
+
0.04,\operatorname{ResolvedConflict}(S)
---------------------------------------

0.08,\operatorname{TokenCost}(S).
]

其中：

* `RankUtility` 使用 candidate rank 或 RRF，不用跨样本未校准的原始分数；
* `IndependentCorroboration` 只在不同 source 对同一 core atom 提供直接证据时计一次；
* `ResolvedConflict` 只在两条 evidence 覆盖同一 atom、且至少为 partial/direct 时计一次；
* 不再单独加入 `map_quality`；
* 不再同时叠加 coverage、key span、confidence、background 等重叠项。

更激进、也更稳健的版本是采用 lexicographic selection：

```text
1. 最大化 unresolved core atom 的 resolution gain；
2. 若相同，优先独立来源 corroboration / conflict resolution；
3. 若仍相同，优先 retrieval rank；
4. 若仍相同，优先更短 evidence。
```

这样基本消除了异质量纲加权的问题。

---

## 9.3 将 penalty 改为硬约束

建议采用：

```text
每个 duplicate_group 最多选择 1 条；
每个 source 最多选择 2 条；
background/context evidence 必须连接到一个未解析 core atom，
或连接到一条已选 direct evidence；
总 evidence tokens 不超过 B；
不强制补足固定的 5 条 evidence。
```

尤其不要只用：

[
|S|\le k.
]

应该使用：

[
\sum_{e\in S}\operatorname{TokLen}(e)\le B.
]

这样可以避免 test 中 evidence units 更长，导致 prompt truncation 或有效 evidence 被截断。

---

## 9.4 使用相对停止条件

将固定：

```text
best_gain <= 0.10
```

改为：

[
\frac{\Delta F_t}{\Delta F_1}<\rho,
]

例如：

[
\rho=0.12.
]

完整停止条件：

```text
达到 core atom resolution threshold，
且当前最佳 marginal gain / 首步 marginal gain < 0.12；
或者没有 evidence 能改变任何 core atom 的状态；
或者达到 token budget。
```

形式化为：

[
\operatorname{Resolve}_{\mathrm{core}}(S)\ge0.75
\quad\land\quad
\frac{\max_e\Delta F(e\mid S)}
{\Delta F(e_1\mid\varnothing)+\epsilon}<0.12.
]

相对阈值比固定 0.10 更能适应不同 claim 和不同 split 的 score scale。

---

# 10. 必须审计 `oracle_likelihood_score`

当前 base-score fallback 路径中存在对 `oracle_likelihood_score` 的引用；在 `qd_union` 路径中似乎不会使用，但需要确认所有 val/test 样本都严格经过该分支。([GitHub][5])

这不一定已经构成 leakage，但建议立即加入防护：

```python
def assert_no_oracle_features(
    candidates: list[dict],
    split: str,
) -> None:
    if split not in {"val", "test"}:
        return

    forbidden = {
        "oracle_likelihood_score",
        "oracle_score",
        "gold_evidence_score",
        "gold_label",
    }

    for idx, item in enumerate(candidates):
        leaked = forbidden.intersection(item)
        if leaked:
            raise RuntimeError(
                f"Forbidden oracle fields in {split} candidate "
                f"{idx}: {sorted(leaked)}"
            )
```

更稳妥的做法是从 selector production code 中完全移除 oracle feature，只在单独的 oracle-upper-bound 脚本中保留。

# 11. 用四组实验确定 gap 的来源

建议严格按以下顺序运行，所有实验使用同一数据、seed、verifier 和 candidate pool。

| 实验 | checkpoint 选择      | logit adjustment    | evidence selector          |
| -- | ------------------ | ------------------- | -------------------------- |
| E0 | 当前 composite score | (\tau=1)            | 当前 graph score             |
| E1 | full-val Macro-F1  | (\tau=1)            | 当前 graph score             |
| E2 | full-val Macro-F1  | (\tau=0)            | 当前 graph score             |
| E3 | full-val Macro-F1  | val-selected (\tau) | calibrated atom-resolution |
| E4 | full-val Macro-F1  | val-selected (\tau) | fixed rank-based top-5     |

解释方式：

* **E1 明显改善**：checkpoint selection 是主要原因；
* **E2 继续改善**：logit adjustment 加剧了 split shift；
* **E3 改善而 E4 不改善**：新 selector 有真实贡献；
* **E4 比当前 selector gap 更小**：现有 graph objective 过拟合；
* **E1–E4 都存在大 gap**：重点转向数据分布、report leakage、prompt truncation 或 label noise。

E4 很重要。一个简单、无参数的 rank top-5 是判断复杂 selector 是否真正导致 gap 的必要控制。

# 12. selector 必须增加的 val/test drift 日志

当前 selector 已记录 objective、coverage、gain 和 stop reason，但需要将每个 score component 分开保存，而不是只保存最终总分。([GitHub][4])

每个样本建议记录：

```json
{
  "split": "val",
  "sample_id": "...",
  "selected_count": 5,
  "selected_tokens": 842,
  "atom_count": 4,
  "core_atom_count": 3,
  "core_resolution": 0.81,
  "rank_utility": 0.43,
  "corroboration_gain": 0.08,
  "conflict_gain": 0.00,
  "duplicate_penalty": 0.00,
  "background_ratio": 0.20,
  "same_source_ratio": 0.40,
  "graph_edge_count": 12,
  "prompt_tokens": 1260,
  "prompt_truncated": false,
  "stop_reason": "relative_gain",
  "prediction_correct": true
}
```

然后比较 val/test：

* selected count；
* selected tokens；
* atom count；
* core atom resolution；
* background/context ratio；
* source diversity；
* graph edge density；
* stop-reason distribution；
* prompt truncation rate。

还应分别计算：

[
\rho_{\mathrm{val}}
===================

\operatorname{Spearman}
(F_{\mathrm{selector}},\mathbf1[\hat y=y]),
]

[
\rho_{\mathrm{test}}
====================

\operatorname{Spearman}
(F_{\mathrm{selector}},\mathbf1[\hat y=y]).
]

若 selector objective 在 val 上与正确率正相关，而在 test 上相关性接近 0 或变负，就能直接证明 score calibration 没有跨 split 泛化。

# 13. 对 test 使用协议的修正

你当前记录中已经出现：

> 保留 val-best alias，但查看 test diagnostics 后发现 checkpoint-400 更好。



这不会直接制造 val/test gap，但会让后续判断受到 test 信息影响。正式投稿实验必须：

```text
所有 checkpoint、tau、selector weights、stop threshold、
prompt style、tight policy 均只由 validation 决定；
配置冻结后再运行 test；
不再根据 test 更换 checkpoint。
```

如果原 test 已被多次检查，投稿版本最好：

* 从训练数据重新划出 development/validation；
* 保留一个此前未查看的 holdout；
* 或使用多个固定 seed split 做 development，最后冻结一次评估。

否则即使 test 指标改善，也很难区分真实泛化和 test-driven selection。

# 14. 推荐最终落地顺序

第一步，不重训，重评所有已有 checkpoints：

```text
full validation Macro-F1
→ 重新建立 best_macro_f1
→ 冻结后 test 一次
```

第二步，重新训练以下最小对照：

```text
early_stopping_metric=macro_f1
mini_val_size=0
logit_adjust.enabled=false
```

第三步，在 validation 上搜索：

```text
tau ∈ {0, 0.25, 0.5, 0.75, 1.0}
```

第四步，加入 selector component drift 日志，并比较：

```text
current graph selector
fixed rank top-5
calibrated atom-resolution selector
```

第五步，再执行 3 个训练 seeds。每个 seed 的 checkpoint 只按 full-val Macro-F1 选；整个配置按：

[
\overline{\mathrm{MacroF1}}_{\mathrm{val}}
------------------------------------------

0.5\operatorname{Std}_{\mathrm{seed}}
]

排序，以避免选择均值略高但方差很大的方案。

## 最核心的修改建议

当前最应该修改的不是某个 graph weight，而是：

```text
checkpoint selection:
macro_f1_plus_true_side
→
full-validation macro_f1
```

随后将 evidence selector 从：

```text
多个重叠特征的固定加权和
+ 固定绝对 gain threshold
```

改为：

```text
soft atom resolution
+ rank-normalized secondary utility
+ duplicate/source/token hard constraints
+ relative stopping
```

我的判断优先级是：

1. **高置信度问题**：checkpoint selection objective 与最终 Macro-F1 不一致；
2. **中高置信度放大因素**：(\tau=1) logit adjustment 和可能的非分层 mini-val；
3. **中等置信度问题**：evidence objective 特征重复计权、绝对阈值和图密度敏感；
4. **待日志验证**：这些因素各自对实际 val/test gap 的贡献比例。

先完成现有 checkpoints 的 full-val 重排序，通常即可在不重训的情况下得到第一轮明确结论。
